# Результат:
# Business Requirements Document (BRD)
## Проект: SafeTech – «КриптоКлюч» (Мобильная квалифицированная электронная подпись)

---

## 1. Введение

### 1.1 Цель документа
Определить бизнес-требования к системе «КриптоКлюч», согласовать видение между стейкхолдерами: бизнес-заказчиками (банки, страховые компании), регуляторами, ИТ-разработкой и конечными пользователями. Документ служит основой для всех последующих технических и проектных артефактов.

### 1.2 Предпосылки и контекст
В настоящее время для подписания документов усиленной квалифицированной электронной подписью (УКЭП) пользователи вынуждены применять физические токены (например, Рутокен, JaCarta) и стационарные компьютеры со специализированным ПО. Это создаёт следующие бизнес‑боли:
- **Низкая мобильность** – сотрудники и клиенты не могут оперативно подписать договор, платёжное поручение или заявление вне офиса.
- **Высокие затраты на обеспечение** – закупка токенов, поддержка драйверов, обучение пользователей, потеря/поломка токенов.
- **Риск компрометации** – физическая потеря токена или несанкционированный доступ к ПК.
- **Замедление бизнес-процессов** – сделки (выдача кредита, открытие счета, страховой полис) требуют личного присутствия или пересылки документов по почте/курьером.

Проект «КриптоКлюч» призван перенести процесс УКЭП в мобильную среду (смартфоны, планшеты) без снижения юридической значимости и уровня безопасности.

### 1.3 Цели и задачи проекта
- **Цель**: Обеспечить возможность подписания юридически значимых документов с мобильных устройств с использованием УКЭП, сократив время операции до 30 секунд и полностью исключив физические токены и стационарные ПК.
- **KPI / метрики успеха**:
  - Время подписания одного документа (от получения запроса до завершения) ≤ 30 секунд (базовое значение: ~15 минут при традиционном процессе).
  - Доля успешно завершённых операций подписания ≥ 99,9% (без учёта сбоев связи у клиента).
  - Количество инцидентов компрометации ключей за период – не более 0 (нулевая толерантность).
  - Рост количества клиентов (юридических лиц и пользователей мобильного банкинга), использующих мобильную подпись, на 200% за первый год после пилота.

## 3. Текущее положение дел (As-Is)

### 3.1 Как работает процесс сегодня (традиционная УКЭП)
1. Пользователь (директор фирмы) подготавливает документ на ПК в учётной системе (например, 1С, интернет-банк).
2. Вставляет USB-токен в компьютер, вводит PIN-код.
3. Система (через криптопровайдер) формирует подпись документа.
4. Подписанный документ отправляется контрагенту/банку/ФНС.
5. При отсутствии токена операция невозможна.

Для мобильных операций (например, выдача кредита в отделении или на выезде) клиент либо:
   - получает документ на бумаге и подписывает ручкой (юридически значимо, но долго и нецифрово), либо
   - использует простую электронную подпись (не имеет полной юридической силы для ряда операций).

### 3.2 Основные проблемы (боли и узкие места)
- **Задержки** от 15 минут до нескольких дней (из-за отсутствия токена/ПК рядом).
- **Дополнительные расходы** на токены (500–3000 руб. на пользователя) + поддержка.
- **Ошибки пользователей** – забытый PIN, потеря токена, несовместимость драйверов с macOS.
- **Безопасность** – токен может быть украден; ПК может быть заражён вредоносным ПО, перехватывающим подпись.
- **Неприменимо для мобильных сотрудников** (курьеры, агенты, выездные консультанты) – они не возят с собой компьютер и токен.

### 3.3 Текстовое описание процесса As-Is (диаграмма активности)
> *Пользователь → открывает ПК → подключает токен → вводит PIN → система проверяет токен → формирует подпись → отправляет документ → отключает токен. Если токен отсутствует – процесс останавливается.*

## 4. Целевое состояние (To-Be)

### 4.1 Как должно работать после внедрения «КриптоКлюча»
1. Пользователь получает push-уведомление или сканирует QR-код в мобильном приложении (банка / страховой).
2. Открывает мобильное приложение «КриптоКлюч» (либо встроенный модуль в приложении банка).
3. Аутентифицируется с помощью биометрии (Face ID / Touch ID) или PIN-кода устройства.
4. Видит суть документа (краткое содержание, сумма, реквизиты).
5. Одним жестом подтверждает подписание.
6. Система генерирует УКЭП на защищённом элементе смартфона (или с использованием распределённого хранения частей ключа на сервере + устройстве) и направляет подписанный документ адресату.
7. Все операции логируются, статус подписания отображается в истории.

### 4.2 Изменения в процессах и ролях
- **УЦ** начинает поддерживать удалённую выдачу сертификатов через мобильное приложение (с видео-идентификацией или через Госуслуги).
- **В организациях** технический администратор получает консоль для управления мобильными ключами сотрудников (блокировка, смена политик).
- **Пользователь** больше не носит токен и не ищет ПК.
- **Мобильное приложение банка** интегрирует SDK «КриптоКлюча» для вызова подписи внутри своего интерфейса.

## 5. Область проекта

### 5.1 Входит в проект (Business scope)
- Разработка мобильного приложения (SDK) для iOS и Android, обеспечивающего генерацию и использование УКЭП.
- Серверная платформа для управления ключами (регистрация устройств, выпуск сертификатов, распределённое хранение компонент ключа, проверка подписей).
- Интеграционные адаптеры с удостоверяющими центрами (квалифицированная выдача сертификатов).
- Административная панель для организаций (добавление/блокировка пользователей, просмотр аудита).
- API для внешних систем (банков, страховых) – запрос на подпись, статус, получение подписанного документа.
- Юридически значимый формат подписанного документа (PKCS#7, XMLDSig с меткой времени).
- Журнал аудита всех операций в защищённом хранилище.

### 5.2 Не входит в проект
- Разработка полноценного мобильного банка или CRM – только модуль подписи.
- Аппаратные токены и их поддержка.
- Интеграция с конкретными учётными системами (1С, SAP) – эту работу выполняют заказчики самостоятельно.
- Переход на зарубежные криптоалгоритмы (только российские ГОСТ).
- Подписание документов для физических лиц без участия УЦ (квалифицированная подпись возможна только при наличии сертификата).

## 7. Ограничения и допущения

### Ограничения
- **Нормативные**:
  - Соответствие 63-ФЗ «Об электронной подписи», 152-ФЗ «О персональных данных».
  - Использование только сертифицированных ФСБ средств криптографической защиты информации (СКЗИ) для мобильных платформ.
  - Требования Центрального банка РФ для кредитных организаций (Положение № 716-П, указание 4859-У).
  - Ограничение на вывоз криптографических средств за пределы РФ – серверная часть должна находиться в российской юрисдикции.
- **Бюджет / сроки** (определяются на фазе планирования) – в рамках данного BRD считается, что проект финансируется, ожидаемый выход на пилот – 4–6 месяцев.

### Допущения
- Удостоверяющие центры, аккредитованные Минцифры, предоставят API для удалённой выдачи квалифицированных сертификатов (по видеосвязи или через ЕСИА).
- Мобильные устройства пользователей поддерживают аппаратный защищённый элемент (Secure Enclave / StrongBox / TEE) для безопасного хранения ключей.
- Внешние системы (банки, страховые) готовы интегрироваться через REST API «КриптоКлюча» – это стандартное требование рынка.
- Операторы сотовой связи не блокируют криптотрафик (ГОСТ-туннели могут быть инкапсулированы в HTTPS).

## Легенда и пояснение

| Элемент | Описание |
|---------|----------|
| **User (Мобильное приложение)** | Клиент, который инициирует подписание документа и подтверждает его биометрией/PIN. |
| **API Gateway** | Единая точка входа для всех запросов; выполняет rate limiting, маршрутизацию, агрегацию. |
| **Сервис авторизации** | Проверяет JWT-токен, права пользователя, а также биометрию (может быть интегрирован с мобильным TEE). |
| **Сервис управления документами** | Хранит метаданные документов, статусную модель, идемпотентность ключей. |
| **Криптографический сервис** | Взаимодействует с защищённым элементом устройства, формирует/проверяет УКЭП, работает с УЦ. |
| **Сервис аудита** | Фиксирует все действия для соответствия 63-ФЗ и внутренней безопасности. |
| **Удостоверяющий центр (УЦ)** | Внешняя система, подтверждающая валидность квалифицированного сертификата. |

### Статусы транзакций (согласно BRD)
- `CREATED` – сессия подписания создана, ожидает подтверждения пользователя.
- `WAITING_SIGNATURE` – пользователь подтвердил, идёт криптографическая операция.
- `SIGNED` – успешное подписание документа.
- `REJECTED` – пользователь отклонил подпись или истекло время (BR-8).
- `ERROR` – ошибка (недействительный сертификат, сетевой сбой и т.п.).
- `TIMEOUT_ERROR` – частный случай ошибки для компенсационных транзакций.

### Идемпотентность и компенсация
- **Идемпотентность** реализована через `idempotencyKey` (BR-5, BR-8). При повторном запросе сервис документов возвращает уже существующий результат, не создавая дубликатов.
- **Компенсационная транзакция** при сбое на этапе формирования подписи (например, потеря связи с устройством) переводит сессию в статус `TIMEOUT_ERROR` и отменяет её, уведомляя администратора. Это предотвращает «зависшие» сессии и повторное использование недействительных ключей.

### Ветвления (alt/opt)
- `alt Идемпотентный повтор` – если операция уже завершена, возвращается кэшированный результат.
- `alt Сертификат недействителен` – блокировка операции, логирование ошибки.
- `alt Пользователь отклонил или таймаут` – штатная обработка отказа.
- `alt Подпись успешно создана` – основной сценарий.

### Соответствие BRD
| BR-ID | Реализация на диаграмме |
|-------|--------------------------|
| BR-1, BR-2 | Инициация + подтверждение через биометрию |
| BR-4 | Проверка сертификата в УЦ |
| BR-5 | Статусная модель (CREATED → WAITING_SIGNATURE → SIGNED/REJECTED/ERROR) |
| BR-6 | Возможность блокировки не показана, но аудит и ошибка сертификата косвенно поддерживают |
| BR-7 | Все логи через сервис аудита |
| BR-8 | Таймаут в 5 минут (реализован через таймер на стороне Crypto/User) |
| BR-9 | Не показан, но подразумевается обработка больших документов через ссылки |
| BR-10 | Отложенное подписание – не является основным сценарием, но может быть добавлено отдельным путём (с офлайн-генерацией и отправкой после восстановления связи). |

Данная диаграмма является эталонной для разработки микросервисов, определения API-контрактов и реализации логики компенсаций. Все последующие артефакты (ER, OpenAPI) должны строго соответствовать этой последовательности.

  id uuid [pk, default: `gen_random_uuid()`]
  user_id uuid [ref: > users.id, not null]
  limit_type varchar(50) [not null] // daily_count, daily_sum
  period_start date [not null] // начало периода (обычно начало дня)
  used_count int [default: 0] // использованное количество
  used_sum decimal(18,2) [default: 0] // использованная сумма
  currency varchar(3) [not null, default: 'RUB']
  updated_at timestamp [not null, default: `now()`]
  // уникальный ключ на пользователя, тип, дату начала

### Индексы (помимо указанных в таблицах)

| Таблица | Индекс | Тип | Обоснование |

### Ограничения целостности (CHECK)

```sql
-- Статусы ограничены допустимыми значениями
ALTER TABLE signing_sessions ADD CONSTRAINT chk_signing_sessions_status 
  CHECK (status IN ('CREATED', 'WAITING_SIGNATURE', 'SIGNED', 'REJECTED', 'ERROR', 'TIMEOUT_ERROR'));

-- Тип лимита
ALTER TABLE document_limits ADD CONSTRAINT chk_document_limits_type 
  CHECK (limit_type IN ('daily_count', 'daily_sum', 'single_sum'));

-- Период лимита положительный
ALTER TABLE document_limits ADD CONSTRAINT chk_document_limits_period 
  CHECK (period_days > 0);

-- Лимиты не могут быть отрицательными
ALTER TABLE document_limits ADD CONSTRAINT chk_document_limits_value 
  CHECK (limit_value >= 0);

-- Пользователь не может быть одновременно удалён и активен (логическое ограничение, можно через триггер)
```

### Каскадные правила (пояснение)

- **RESTRICT** – запрещает удаление родительской записи, если существуют зависимые записи. Применено для `users`, `documents`, `certificates`, `signing_sessions`, `document_limits`, чтобы гарантировать целостность аудита и невозможность удаления пользователя с активными сессиями или сертификатами (требование BR-6, BR-7).
- **CASCADE** для `devices` – при удалении пользователя устройства каскадно удаляются (менее критично, так как сессии уже не могут быть активны).
- **SET NULL** для `audit_logs` – логи остаются даже после удаления пользователя (соблюдение регуляторных требований по неизменяемости аудита).

### Примечание по соответствию BRD

- **BR-5 (статусная модель)** – реализована через `signing_sessions.status` + `audit_logs`.
- **BR-8 (время жизни 5 минут)** – поле `expires_at` с индексом для очистки.
- **Идемпотентность** – уникальный `idempotency_key` в `signing_sessions`.
- **Лимиты и проверки** – хотя в BRD нет явных сумм, добавлены таблицы `document_limits` и `rate_limits` для возможного будущего расширения (например, ограничение на количество подписей в день для физлиц). При необходимости эти сущности легко деактивировать.
- **Безопасность и аудит** – `audit_logs` фиксирует каждое действие (BR-7). Хранение IP и User-Agent.
- **Ключи и сертификаты** – таблица `certificates` связана с устройством и пользователем, поддерживает статусы (активный/отозванный). Не хранит закрытый ключ (он в защищённом элементе устройства или распределённо), только метаданные и отпечаток публичного ключа.

Данная ER-диаграмма является логической основой для физической реализации в реляционной СУБД (PostgreSQL, Oracle или аналогичной). Все идентификаторы – UUID для распределённой генерации. Тип `jsonb` для гибких метаданных.

## 📌 Обязательные требования к спецификации OpenAPI 3.1.0

### 1. Корневая структура (обязательные поля на верхнем уровне)

Согласно OpenAPI 3.1, корневой объект **обязан** содержать:
- `openapi` — строка с версией (обязательно: `"3.1.0"`)[reference:1]
- `info` (с обязательными полями `title` и `version`)[reference:2]
- хотя бы один из: `paths`, `components` или `webhooks`[reference:3]

Все остальные поля (`servers`, `security`, `tags`) — опциональны, но рекомендуются для финтех-сценариев[reference:4]

### 2. Секция `components` — допускается **строго один раз**

`components` — это **контейнер для всех переиспользуемых объектов**, которые затем ссылаются через `$ref`.[reference:5]  
⚠️ **Критическое правило:** в документе не может быть двух секций `components`! Корневой YAML-объект может содержать **только один ключ `components`** на верхнем уровне.

Внутри `components` можно размещать следующие объекты (все опциональны):[reference:6]
- `schemas` — модели данных из ER-диаграммы (User, Transaction, Account…)
- `parameters` — общие параметры (например, `page`, `limit`, `sort`)
- `responses` — стандартные ответы (ошибки, успешные создания)
- `securitySchemes` — схемы аутентификации (JWT, API Key, Basic Auth)
- `examples` — общие примеры тел запросов/ответов
- `requestBodies` — общие тела запросов

### 3. Правила `$ref` (ссылки на компоненты)

- Ссылка **всегда** начинается с `#/components/{type}/{name}`[reference:7]
- В YAML нельзя ставить `$ref` на одном уровне с другими полями (у `$ref` должны быть отдельные поля рядом) — корректно либо `$ref`, либо явное описание, но не оба сразу.

### 4. Уникальность `operationId`

Каждый эндпоинт+метод (GET /payments, POST /payments) должен иметь **уникальный** `operationId`. Одинаковые `operationId` в одном документе недопустимы.[reference:8]

### 5. Обязательные атрибуты для моделей и параметров (безопасность финтеха)

- В каждом `schema object` (модели данных) обязательно указывать `type` и, где необходимо, `required`。[reference:9]
- Для числовых финансовых полей (`amount`, `commission`, `balance`) обязательно указывать `minimum` и `maximum` согласно BRD, а также `type: number`, `format: decimal` (или `double`, если допустимо).[reference:10]
- Для строковых полей с фиксированным набором значений обязательно использовать `enum` (статусы транзакций, типы валют).[reference:11]
- Для транзакционных эндпоинтов (POST /transfer) обязательно указание **идиемпотентности** — заголовок `Idempotency-Key` в параметрах.

### 6. Полнота описания ответов и ошибок

- Для каждого эндпоинта должны быть описаны минимум **200/201 и 4xx ошибки**: 400 (Bad Request), 401 (Unauthorized), 403 (Forbidden), 404 (Not Found), 422 (Validation Error).[reference:12]
- Для 5xx ошибок допустимо дать `default`-ответ с общей схемой ошибки.

### 7. Соблюдение типов данных и ограничений JSON Schema 2020-12 (OpenAPI 3.1)

- В 3.1 не используй устаревшее `nullable: true` — используй вместо этого `type: ["string","null"]`（TODO: need a valid citation for this rule, as currently cited result does not contain this specific guideline)
- `readOnly` и `writeOnly` допустимы (например, `id` и `createdAt` — `readOnly: true`).[reference:13]

### 8. Единообразие именования и документации

- Используй `camelCase` для всех имён полей моделей и параметров.[reference:14]
- Для каждого эндпоинта (`paths/*`) и параметра обязательно наличие поля `description` (хотя бы краткого).[reference:15]

### 9. Соблюдение нотации YAML

- В YAML массив должен начинаться с `-`.[reference:16]
- Отступы должны быть строго одинаковыми (обычно 2 или 4 пробела, без символов табуляции).

## 🔧 Процесс генерации OAS (пошаговая инструкция)

1. **Создай корневой объект** с полями `openapi: "3.1.0"`, `info` (title и version из BRD).
2. **Создай секцию `servers`** (хотя бы один базовый URL, например `https://api.{{PROJECT_NAME}}.com/v1`).
3. **Создай секцию `paths`** — перечисли все эндпоинты из BRD и Sequence (включая создание операции, получение статуса, отмену, историю).
4. **Создай секцию `components`** (один раз!). Внутри:
   - `schemas` — все модели данных, соответствующие ER-диаграмме. У каждой модели перечисли поля, типы, required, enum.
   - `parameters` — общий `id` параметр (`in: path`), пагинационные параметры.
   - `responses` — шаблоны ошибок (например, `NotFound`, `ValidationError`).
   - `securitySchemes` — схему аутентификации (например, `BearerAuth`).
5. **В `paths` для каждого метода** явно опиши:
   - `operationId` (уникальный строковый идентификатор, например `createTransaction`).
   - `parameters` (если есть query/path/header параметры).
   - `requestBody` (для POST/PUT методов), включая `content` с ссылкой на схему из `components/schemas`.
   - `responses` со ссылками на схемы из `components`.
6. **Добавь примеры** для одного успешного запроса и одного ошибочного.

```yaml
openapi: 3.1.0
info:
  title: TryHouse Payments API
  version: 1.0.0
servers:
  - url: https://api.tryhouse.com/v1
    description: Production server
components:
  securitySchemes:
    bearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
  schemas:
    Transaction:
      type: object
      required:
        - id
        - amount
        - status
      properties:
        id:
          type: string
          readOnly: true
        amount:
          type: number
          minimum: 0.01
          maximum: 1000000
        status:
          type: string
          enum: [CREATED, PENDING, PROCESSING, SUCCESS, FAILED, CANCELLED, REFUNDED]
paths:
  /transactions:
    post:
      operationId: createTransaction
      security:
        - bearerAuth: []
      requestBody:
        required: true
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/CreateTransactionRequest"
      responses:
        "201":
          description: Transaction created
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/Transaction"
        "400":
          $ref: "#/components/responses/ValidationError"
        "401":
          description: Unauthorized
        "422":
          $ref: "#/components/responses/ValidationError"

```
